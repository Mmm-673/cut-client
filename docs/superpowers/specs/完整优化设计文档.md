### 1.1 Request URL 构造逻辑 Bug 修复（003）

**严重程度**：HIGH | **工作量**：5 min | **风险**：极低

**文件**：`utils/request.js:141`

**问题**：
```javascript
url: config.baseUrl || baseUrl + config.url
```
由于 `||` 优先级低于 `+`，实际执行 `config.baseUrl || (baseUrl + config.url)`，当传了 `baseUrl` 时完全丢弃 `config.url`。

**修复**：
```javascript
url: (config.baseUrl || baseUrl) + config.url
```

**验证**：全局搜索 `baseUrl:` 确认调用点 → 修复后验证 URL 正确 → 核心流程跑通

### 1.3 确认订单页 Storage 数据校验（006）

**严重程度**：HIGH | **工作量**：0.5 天 | **风险**：中

**文件**：`subpkg/booking/confirm.vue`

**问题**：订单金额、时长等关键数据从 `uni.getStorageSync('createdOrderData')` 读取，用户可篡改。

**修复方案（方案 A：全量从后端获取）**：

1. onLoad 时从 storage 提取 `orderId`
2. 有 orderId：显示 loading → 调 `getOrderDetail(orderId)` → 用后端数据完全替换
3. 无 orderId（初次下单）：走原有创建流程
4. 保留非安全敏感的草稿数据（selectedCoach、时间选择、球厅选择等）

**加载体验**：有 orderId 时先显示骨架屏/loading，不显示旧 storage 数据（避免跳变）

**验证**：
- 正常流程金额正确
- 篡改 storage 后金额仍正确
- 无 orderId 走创建流程正常
- 断网有错误提示和重试

### 5.3 跨页面数据用 Store 替代 Storage 传递（047）

**工作量**：1 天

**当前问题**：跨页面数据传递大量依赖 `uni.setStorageSync`，如教练选择、球厅选择、订单草稿等。

**方案**：
- 使用 Pinia store 管理跨页面共享的临时状态

- `selectedVenue` → booking store

**保留在 storage 的**：
- token 相关
- 用户信息
- 主题设置
- 所有需要持久化的数据

## Phase 6：性能优化

**目标**：提升渲染性能、网络性能，修复内存泄漏。
**预估周期**：5-7 天
**风险等级**：低到中

### 6.1 v-for key 替换 index（037）

**工作量**：0.5 天 | **预期收益**：diff 效率 +20-40%

**问题**：大量 `v-for="(item, index) in list" :key="index"` 使用 index 作为 key，列表数据变化时 diff 效率低。

**方案**：
- 用业务唯一 ID（id、orderId、coachId 等）替代 index
- 没有唯一 ID 的场景，使用 `index + '-' + item.name` 等组合方式
- 确认每项都有稳定唯一标识后再改

**检查范围**：全局搜索 `v-for.*:key="index"`

### 6.2 图片懒加载（042）

**方案**：
- 列表中的图片使用 `lazy-load` 属性（uni-app 原生支持）
- 或使用 `uni-lazy-load` 组件
- 头像、商品图等非首屏关键图片都开启懒加载

**范围**：
- 教练列表头像
- 球厅列表图片

### 6.3 订单列表事件监听清理（050）

**工作量**：0.5 h | **风险**：低

**问题**：`pages/order/list.vue` 中的 `uni.$on` 事件监听在页面卸载时未正确清理，导致内存泄漏。

**方案**：
- 在 `onUnload` 或 `onHide` 中调用 `uni.$off` 清理
- 使用 `onUnmounted` 生命周期钩子（Vue 3 Composition API）
- 检查所有使用 `uni.$on` 的页面，确保都有对应的 `$off`

### 6.4 订单详情定时器统一管理（052）

**工作量**：0.5 天 | **风险**：中

**问题**：订单详情页有多个定时器（倒计时、轮询、计时刷新等），分散在各处，页面卸载时可能遗漏清理。

**方案**：
- 所有定时器统一收集到一个数组中管理
- 提供 `clearAllTimers()` 函数
- 在 `onUnload` / `onUnmounted` 中统一清理
- 与 5.1 的 `useOrderTimer` composable 结合实现

### 6.5 WS 去重 Set 容量限制（070）

**工作量**：0.5 h | **风险**：低

**问题**：WebSocket 消息去重的 Set 只增不减，长期运行后内存持续增长。

**方案**：
- 设置容量上限（如 1000 条）
- 超过上限时删除最早的条目（可用环形数组或 LRU 策略）
- 或改用时间窗口策略，只保留最近 N 分钟的消息 ID

### 6.6 我的页订单懒加载 + pageSize=5（040）

**工作量**：0.5 天 | **预期收益**：请求数从 7→1

**当前问题**：我的页加载时同时请求全部 7 个状态的订单数量，每个都单独请求，浪费资源。

**方案**：
- 初始只加载默认 tab 的订单（或不加载，只显示数量）
- 切换 tab 时才请求对应状态的订单列表
- pageSize 改为 5（我的页只显示少量订单，不需要 10 条）
- 订单数量从用户信息接口或单独的统计接口获取

### 6.7 轮询退避策略 + onHide 暂停（043）

**工作量**：0.5 天 | **预期收益**：请求量 -40-60%

**问题**：支付轮询等轮询请求间隔固定，且页面在后台时仍在轮询。

**方案**：
- 实现指数退避：前几次间隔短（如 3s），后续逐渐加长（5s → 10s → 30s）
- 设置最大间隔上限（如 30s）
- 页面 `onHide` 时暂停轮询，`onShow` 时恢复
- 设置最长轮询时间（如 5 分钟），超时后停止并提示

**应用范围**：
- 支付结果轮询
- 订单状态轮询
- 其他周期性请求

### 6.9 首页 WS 订阅 onHide 取消（051）

**方案**：

### 6.10 onShow 按需刷新（dirty flag）（038）

**工作量**：1 天 | **预期收益**：重复请求 -60%

**问题**：很多页面在 `onShow` 时无条件刷新数据，即使数据没有变化。

**方案**：
- 引入 dirty flag 机制：只有相关数据变化时才刷新
- 触发 dirty 的场景：
  - 订单状态变更（通过 uni.$emit 通知）
  - 用户信息修改
  - 支付成功
  - 下单成功
- `onShow` 时检查 dirty flag，为 true 才刷新，刷新后重置
- 与 store 结合使用效果更佳

**应用范围**：
- 首页
- 订单列表页
- 我的页
- 订单详情页

### 6.11 模板计算逻辑预计算（039）

**工作量**：1 天 | **预期收益**：滚动 JS 时间 -20-30%

**问题**：模板中有大量计算逻辑（如价格格式化、状态判断、时间格式化等），每次重新渲染都要重新计算。

## 实施总原则

1. **不破坏现有功能** — 所有优化都是重构性质，不改变用户可见行为
2. **渐进式推进** — 每个改动独立验证，不堆在一起一次上线
3. **先低风险后高风险** — 从简单的入手，建立信心和节奏
4. **每阶段可回滚** — 每个阶段的改动相对独立，出问题可单独回滚
5. **不操作 git** — 所有改动只在本地，不上传不提交

- **编译通过**：H5、微信小程序、App 三端均可正常构建
