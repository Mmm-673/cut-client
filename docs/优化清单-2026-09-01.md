## 🔴 P0 紧急（安全 & 功能正确性）

> 建议优先处理，存在安全隐患或功能缺陷

### [❌ ] 001. 路由权限形同虚设
- **严重程度**：CRITICAL
- **文件**：`permission.js`
- **问题**：只做了「已登录用户访问登录页跳首页」，未登录用户可以直接访问订单、钱包、设置等所有需要登录的页面
- **风险**：用户体验差（进入页面空白/报错），页面结构可被探测，若后端有疏漏直接泄露数据
- **方案**：建立完整的路由白名单 + 登录检查机制
- **预估工作量**：0.5 天
- **决策**：____

### [ ❌] 002. 钱包支付空函数（误调用会假支付成功）
- **严重程度**：CRITICAL
- **文件**：`utils/payment.js:323-330`
- **问题**：`walletPay()` 是空实现，直接 resolve 成功。当前主流程未调用，但未来重构时误调用会导致「假支付成功」
- **方案**：删除该函数，或加 `throw new Error('Not implemented')` 防止误调用
- **预估工作量**：10 分钟
- **决策**：____

### [✅  ] 003. Request URL 构造逻辑 Bug
- **严重程度**：HIGH
- **文件**：`utils/request.js:141`
- **问题**：`url: config.baseUrl || baseUrl + config.url` 由于运算符优先级，传了 `baseUrl` 时会完全丢弃 path 部分
- **方案**：改为 `url: (config.baseUrl || baseUrl) + config.url`
- **预估工作量**：5 分钟
- **决策**：____

### [ ❌] 004. Refresh Token 通过 URL 参数传递
- **严重程度**：HIGH
- **文件**：`api/auth.js`
- **问题**：refreshToken 用 GET + query 参数传递，会出现在服务器 access log、浏览器历史、Referer 中
- **方案**：改为 POST 请求，将 refreshToken 放在请求体中
- **预估工作量**：0.5 小时
- **决策**：____

### [ ❌] 005. WebSocket Token 通过 URL Query 传递
- **严重程度**：HIGH
- **文件**：`utils/websocket.js:50`
- **问题**：access token 放在 WebSocket URL 的 query string 中，同样有日志泄露风险
- **方案**：连接建立后通过第一条消息认证，或使用 Sec-WebSocket-Protocol header
- **预估工作量**：0.5 天（需要后端配合）
- **决策**：____

### [✅  ] 006. 确认订单页数据从 Storage 读取无校验
- **严重程度**：HIGH
- **文件**：`subpkg/booking/confirm.vue:1173-1186`
- **问题**：订单金额、时长等关键数据从 `uni.getStorageSync('createdOrderData')` 读取，用户可篡改 storage 中的金额（最终以后端为准，但展示不一致会引发投诉）
- **方案**：以 orderId 为准从后端拉取订单详情展示，storage 仅存非关键缓存
- **预估工作量**：0.5 天
- **决策**：____

### [✅  ] 007. 3 个空 catch 块（静默失败）

### [❌ ] 008. 定位静默失败（Promise 空 catch）
